# Project structure

The folder tree of a bounded context, the naming table, and what each layer may reference.

## One folder per bounded context, four layers inside

The project is a single ASP.NET Core web project. Every bounded context is a folder next to `Program.cs`, and every one of them has the same four layers with the same subfolders. The namespace follows the folder, always: `QuickBite.Platform.Ordering.Domain.Model.Aggregates` is the folder `Ordering/Domain/Model/Aggregates`.

```
QuickBite.Platform/
├── QuickBite.Platform.csproj
├── Program.cs                                 the composition root: services, pipeline, one line per context
├── Migrations/                                EF Core migrations, generated by dotnet ef
├── Ordering/                                  a bounded context
│   ├── Domain/
│   │   ├── Model/
│   │   │   ├── Aggregates/                    Order
│   │   │   ├── Entities/                      OrderLine
│   │   │   ├── ValueObjects/                  CustomerId, Money, OrderStatus
│   │   │   ├── Commands/                      OpenOrderCommand, AddOrderLineCommand, PlaceOrderCommand, …
│   │   │   ├── Queries/                       GetOrderByIdQuery, GetOrdersByCustomerIdQuery, …
│   │   │   └── Events/                        OrderPlacedEvent
│   │   ├── Repositories/                      IOrderRepository
│   │   └── Services/                          a domain service, only when a rule belongs to no single aggregate
│   ├── Application/
│   │   ├── CommandServices/                   IOrderCommandService
│   │   ├── QueryServices/                     IOrderQueryService
│   │   ├── Acl/                               <Context>ContextFacade, when this context is a provider
│   │   └── Internal/
│   │       ├── CommandServices/               OrderCommandService
│   │       ├── QueryServices/                 OrderQueryService
│   │       ├── EventHandlers/                 OrderPlacedEventHandler
│   │       └── OutboundServices/Acl/          ExternalCustomerService
│   ├── Infrastructure/
│   │   ├── Persistence/EntityFrameworkCore/
│   │   │   ├── Configuration/                 OrderConfiguration, OrderLineConfiguration
│   │   │   └── Repositories/                  OrderRepository
│   │   └── DependencyInjection/               OrderingContextExtensions — AddOrderingContext()
│   └── Interfaces/
│       ├── Rest/                              OrdersController
│       │   ├── Resources/                     OrderResource, OpenOrderResource, AddOrderLineResource, …
│       │   └── Transform/                     OpenOrderCommandFromResourceAssembler, OrderResourceFromEntityAssembler, …
│       └── Acl/                               I<Context>ContextFacade, when this context is a provider
├── Customers/                                 another bounded context, same shape
├── Iam/                                       the identity context, same shape plus Infrastructure/Hashing and /Tokens
└── Shared/                                    the shared kernel — see shared-kernel.md
```

Three things about the tree that are decisions, not accidents:

- **Commands and queries live in the domain**, not in the application layer. They are part of the model: an `OpenOrderCommand` is a sentence in the ubiquitous language, and the aggregate takes it as a constructor argument. The application layer only *executes* them.
- **The service interfaces live in `Application/CommandServices` and `Application/QueryServices`; their implementations in `Application/Internal`.** The application layer declares the use cases it offers and keeps how it does them internal. A controller depends on the interface and never sees the implementation.
- **The mapping lives in `Infrastructure`.** An `IEntityTypeConfiguration<T>` per aggregate says how it is stored; the domain classes carry no attribute from EF Core or System.Text.Json. The one concession the domain makes to persistence is a private parameterless constructor for EF Core to materialize the object — see `aggregates.md`.

What each layer is for:

| Layer | Holds | Never holds |
| --- | --- | --- |
| `Domain` | aggregates, entities, value objects, commands, queries, events, repository interfaces | a `using Microsoft.…`, a configuration, another context's types |
| `Application` | the service interfaces and their implementations, event handlers, outbound ACL services, the facade this context exposes | business rules — if an `if` decides what the domain allows, it belongs in the aggregate |
| `Infrastructure` | EF Core configurations and repositories, adapters for the outbound ports (hashing, tokens, external APIs), the context's registration | logic that reads a domain object to decide something |
| `Interfaces` | controllers, resources, assemblers, the facade interface other contexts call | a domain type in an endpoint's signature or a resource; a repository |

## Naming table

The same name, spelled the same way, everywhere. Given an aggregate `Order` in the context `Ordering`:

| Thing | Name | Folder |
| --- | --- | --- |
| Aggregate root | `Order` | `Domain/Model/Aggregates` |
| Entity inside the aggregate | `OrderLine` | `Domain/Model/Entities` |
| Value object | `Money`; enum `OrderStatus` | `Domain/Model/ValueObjects` |
| Reference to another aggregate | `CustomerId` | `Domain/Model/ValueObjects` |
| Command | `<Verb><Aggregate>Command` — `OpenOrderCommand`, `PlaceOrderCommand`, `AddOrderLineCommand` | `Domain/Model/Commands` |
| Query | `Get<Aggregate>By<Field>Query`, `GetAll<Aggregates>Query`, `Get<Aggregates>By<Field>Query` | `Domain/Model/Queries` |
| Domain event | `<Aggregate><PastParticiple>Event` — `OrderPlacedEvent` | `Domain/Model/Events` |
| Repository interface | `IOrderRepository` | `Domain/Repositories` |
| Domain service | named for what it decides — `DeliveryFeeCalculator` | `Domain/Services` |
| Service interfaces | `IOrderCommandService`, `IOrderQueryService` — every method is `Handle` | `Application/CommandServices`, `…/QueryServices` |
| Service implementations | `OrderCommandService`, `OrderQueryService` | `Application/Internal/CommandServices`, `…/QueryServices` |
| Event handler | `OrderPlacedEventHandler`, method `Handle(OrderPlacedEvent, …)` | `Application/Internal/EventHandlers` |
| Outbound ACL service | `ExternalCustomerService` | `Application/Internal/OutboundServices/Acl` |
| Facade this context exposes | `ICustomersContextFacade` / `CustomersContextFacade` | `Interfaces/Acl` / `Application/Acl` |
| Mapping | `OrderConfiguration : IEntityTypeConfiguration<Order>` | `Infrastructure/Persistence/EntityFrameworkCore/Configuration` |
| Repository | `OrderRepository : BaseRepository<Order>, IOrderRepository` | `Infrastructure/Persistence/EntityFrameworkCore/Repositories` |
| Registration | `OrderingContextExtensions.AddOrderingContext()` | `Infrastructure/DependencyInjection` |
| Controller | **plural** — `OrdersController` at `/api/v1/orders` | `Interfaces/Rest` |
| Resources | `OrderResource` (response), `OpenOrderResource`, `AddOrderLineResource` (requests) | `Interfaces/Rest/Resources` |
| Assemblers | `OpenOrderCommandFromResourceAssembler.ToCommandFromResource(resource)`, `OrderResourceFromEntityAssembler.ToResourceFromEntity(entity)` | `Interfaces/Rest/Transform` |
| Route parameter | `{orderId:int}`, never `{id}` | |
| Database table | `orders`, `order_lines` — plural snake_case, produced by the naming convention | |

A context folder is a PascalCase noun or gerund (`Ordering`, `Customers`, `MenuManagement`); a REST path is plural kebab-case (`/api/v1/menu-items`), produced from the controller's name by the route convention. The generator derives every spelling from the two names you give it — see `adding-a-resource.md`.

**One type per file**, named like the type. The exceptions are pairs that only make sense together: `Result<T>` and `Result` share `Result.cs`.

**Name a context after what it owns, and the entity after the thing.** `Ordering` with `Order` works; a context called `Order` with an entity `Order` does not compile — inside the context, `Order` is the namespace (CS0118). An entity that shares its name with a type every file already sees — `Task`, `Path`, `File`, `Thread`, `Timer`, `Range`, `Index`, `Host`, `Endpoint`, or the kernel's `Result` and `Error` — makes every reference ambiguous (CS0104); one named `Event` puts the C# keyword `event` where a variable name goes. Each was measured, and the generator refuses all of them, along with the other keywords and the types of the same namespaces; the fix is always a more specific name in the ubiquitous language (`KitchenTask`, `DeliveryRoute`).

**Two contexts, two words.** A `Product` in `Catalog` and another in `Inventory` compile — they live in different namespaces — and then collide where names are global: the table (`products`, the model refuses to build), the route (`/api/v1/products`, every request a 500) and, without the kernel's schema ids, the API description. The generator refuses an entity another context already uses; the fix is the word each context really uses (`Product`, `StockItem`), or, when it is the same word, a table and route of its own — see `persistence.md`.

## What may reference what

Dependencies point inward: `Interfaces` and `Infrastructure` know `Application` and `Domain`; `Application` knows `Domain`; `Domain` knows nothing outside itself. Another bounded context is reached only through its facade (see `anti-corruption-layer.md`), so the one reference from one context's `Application` to another context's code is to `<Provider>/Interfaces/Acl`.

In a single project nothing enforces this; two `grep`s check it, and both should print nothing but the facades:

```bash
grep -rnE '^using (Microsoft\.|.*\.(Application|Infrastructure|Interfaces)\b)' --include='*.cs' */Domain
grep -rnE '^using .*\.(Infrastructure|Interfaces)\b' --include='*.cs' */Application
```

The second prints the `using …Interfaces.Acl;` lines of the facades and of the external services that consume them — those are the design, not a leak. Both check the `using` lines that are written; a web project's implicit usings also put `Microsoft.AspNetCore.Http`, `Microsoft.Extensions.Logging` and their neighbours in scope in every file, the domain's included, so an `ILogger` or an `HttpContext` in a domain class compiles without a `using` and passes the grep. Reading the domain is still part of the review.

When a team wants the compiler to enforce the rule, the usual step is a solution with one project per layer (`QuickBite.Ordering.Domain`, `.Application`, …), or an architecture test with a library such as NetArchTest. Both cost more than they buy in a project this size; the folders, the namespaces and the two commands above are the house style.
